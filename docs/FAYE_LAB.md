# FayE Lab: training, tuning, and strength validation

FayE Brain separates **learning**, **parameter tuning**, **feature acceptance**, and **external benchmarking**. A match against Stockfish is not itself training.

## Four different jobs

1. **Neural training** produces model weights from labeled positions.
2. **Offline validation** checks whether the learned target generalizes to held-out positions.
3. **Candidate-vs-parent testing** decides whether a concrete engine change improves playing strength.
4. **Best-FayE-vs-Stockfish testing** measures the accepted FayE engine against the latest official Stockfish master.

The development loop is:

```text
positions -> teacher labels -> train model -> offline validation
                                      |
                                      v
                               FayE candidate
                                      |
                            candidate vs parent
                                      |
                               paired SPRT
                              /           \
                          reject          accept
                                            |
                                           merge
                                            |
                               best FayE vs Stockfish
```

## Training data

The pilot uncertainty target is generated by comparing a shallow search with a deeper teacher search for the same position. The dataset stores:

- FEN;
- shallow and deep scores;
- shallow and deep best moves;
- search depth/nodes when available;
- evaluation swing;
- whether the best move changed;
- a continuous uncertainty target in `[0, 1]`;
- a 24-value cheap bootstrap feature vector.

The bootstrap feature vector is intentionally independent of internal NNUE state. Its purpose is to test whether the **target** is useful before investing in a runtime NNUE-head integration. If the target works, the input can later be replaced by NNUE activations while preserving the label pipeline.

By default, training and engine-strength opening sets should be different. For example, training may sample `popularpos_lichess_v3.epd`, while strength tests use UHO openings.

## Training hyperparameters

The `FayE uncertainty training` workflow exposes values that can change between runs:

- number of teacher positions;
- shallow teacher nodes;
- deep teacher nodes;
- hidden size;
- epochs;
- batch size;
- learning rate;
- weight decay;
- random seed;
- dataset profile.

Each run exports the labeled JSONL dataset, PyTorch checkpoint, quantized INT8 JSON, and `metrics.json`.

A lower validation loss does **not** automatically mean a stronger chess engine. The trained candidate must ultimately survive engine testing after runtime integration.

## Candidate vs parent

This is the primary feature acceptance test.

Examples:

- FayE parent vs FayE + uncertainty-guided LMR;
- FayE parent vs FayE + policy move ordering;
- accepted FayE vs the same engine with one parameter changed.

The test uses paired openings. Every opening is played twice with colors reversed. Fastchess pentanomial/SPRT output is the decision signal.

## External benchmark vs Stockfish

The existing `FayE vs Stockfish (Fishtest-style)` workflow clones the latest official Stockfish master at job start. This answers a different question:

> How does the current best accepted FayE compare with current Stockfish?

It is **not** the primary accept/reject test for an individual FayE feature.

## SPSA-style search tuning

`FayE SPSA-style tuner` is a small transparent local tuner. It is inspired by the same idea used by Fishtest: perturb several scalar parameters together, play paired games, then move the center values toward the better perturbation.

It is deliberately labeled **SPSA-style** rather than claiming byte-for-byte identity with the Fishtest server implementation.

The first experiment tunes:

- `FayE_ComplexityLMRWeight`;
- `FayE_ComplexityThreshold`;
- `FayE_ComplexityLMRCap`.

The experimental source change lives in `experiments/patches/complexity-lmr.patch`. This keeps `main` clean until the feature passes testing. The patch adds UCI options only to the candidate build.

### Why keep features as patches before acceptance?

A proposed idea should not silently become part of the engine. The lab workflow can apply a patch to a temporary candidate worktree, test it against an unmodified parent, and only then decide whether to merge the source change.

## Experiment registry

Every serious experiment should receive an ID such as `FAYE-0001` and record:

- feature hypothesis;
- parent SHA;
- candidate ref/patch;
- training artifact, if any;
- parameter values;
- opening set;
- time control;
- game count or SPRT bounds;
- NPS cost;
- result;
- final decision.

Use `scripts/register_experiment.py` to create a new manifest without overwriting an existing ID.

## Acceptance discipline

Recommended order:

1. compile and benchmark correctness;
2. offline target/model validation;
3. short-TC candidate-vs-parent screening;
4. SPSA-style parameter tuning if the feature is promising;
5. fresh candidate-vs-parent SPRT with tuned parameters;
6. longer-TC verification;
7. merge only if reproducible;
8. compare the new best FayE to latest Stockfish.

Do not reuse the exact same games for both parameter tuning and the final acceptance test. Use a new seed and preferably a fresh opening slice for confirmation.
